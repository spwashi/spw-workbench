# UX Audit — Spw Workbench
**Date:** 2026-02-15  
**Scope:** Document Navigator · Settings Panel · Keybinding Geology · Context Engine  
**Theme under test:** High Contrast Dark (Atelier family)  
**Viewports tested:** 375px (mobile), 600px (tablet), ~800px (narrow desktop), 1440px (full desktop)

---

## Executive Summary

The workbench is already a sophisticated, well-structured tool. The visual hierarchy (Editor → Inspector → Context) is effective, the disclosure/LoD/perspective axis system is well-conceived, and the Spw copy-mode vocabulary work has resolved prior ambiguities. This audit identifies **14 actionable findings** ranging from contrast polish to responsiveness gaps, organized by the categories requested.

---

## 1. Theme Differentiation & Contrast

### ✅ Strengths
- **Panel depth hierarchy works well.** The Editor panel is visibly brighter than the Inspector, which is brighter than the Context Engine. This naturally guides the eye to the authoring surface.
- **Operator vibrancy is excellent.** `!boon`, `@out`, and string literals are color-coded with distinct, high-saturation hues against the dark background. Instantly scannable.
- **Badge/tag contrast** (`VIS · BAS`, `MEDIUM`, `DOC`, `FINE`, `COARSE`) uses pill shapes with strong color contrast. They're legible at all LoD levels.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **T-1** | **"Editing" mode button near-invisible** | 🔴 High | In the ACTIVE CONTEXT / PRIMARY MODES section (Context Engine), the "Editing" button has extremely low contrast — olive/khaki text on a similarly toned background. It almost disappears compared to the "Visual" button (teal, strong contrast). At narrow widths this is even worse. |
| **T-2** | **System State card borders blend into background** | 🟡 Medium | The green-tinted borders on the 2×4 System State grid are subtle. On the "high contrast dark" theme, these thin 1px borders are easy to miss, especially at LoD Fine where the panel information density is lower. Consider 2px borders or a slight background fill difference between cards. |
| **T-3** | **Footer status bar text too dense at full width** | 🟡 Medium | The footer bar packs keybindings, mode hints, focus path, and stage info into a single line. At 1440px it's mostly legible, but the yellow `GEOLOGY` badge, green accents, and white text all compete. No clear visual grouping separates the three logical zones (keybinding hints / status / stage). |

## 2. Perspective & LoD Controls — Utility Evaluation

### ✅ Strengths
- **LoD transitions are clearly differentiated:**  
  - **Fine** → Minimal content in Context Engine, token-level inspector tab visible.  
  - **Medium** → Full System State grid, block-level tabs.  
  - **Coarse** → Compact view with Regions section, mode shortcuts (i/v/t), and tab shortcuts (AST/TOKENS/FLOW/STEPS).
- **LoD badge updates consistently** across Editor header, Context header, and footer bar. The user always knows which level they're at.
- **Perspective/Copy Mode vocabulary** resolved prior ambiguities (e.g., `?traverse` vs `?search` vs `?walk`). The COPY/PASTE badge appears on the Context Engine when in copy mode.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **P-1** | **"AMBIENT / MED…" badge is truncated and cryptic** | 🟡 Medium | The genre/atmosphere badge in the Editor and Context headers reads `AMBIENT / MED…` — the truncation hides meaning. "MED…" could mean Medium, Meditation, or Media. At narrow width it truncates further. Consider either showing the full label or using a shorter canonical abbreviation. |
| **P-2** | **Coarse LoD mode shortcuts lack affordance** | 🟡 Medium | At Coarse LoD, the `i INSERT`, `v VISUAL`, `t TRANSFORM` buttons in the Regions section are styled as flat gray pills with no hover indication visible in the static screenshot. They don't communicate "pressable" as clearly as the Primary Modes buttons (which have color fills). |
| **P-3** | **Disclosure level row (BASIC/GUIDE/DEEP/FULL) has no active-state differentiation at narrow widths** | 🟡 Medium | At 800px+, the active disclosure pill (`BASIC`) has a green fill. At 375px, the row compresses and the active state is less visually distinct — the pills become smaller and the fill is harder to perceive. |

## 3. Tabindex & Keyboard Accessibility

### ✅ Strengths
- **Focus path telemetry** in the Context Engine is excellent. It shows the full DOM ancestry (`app > main > geology > keybinding-geology`) so the user (and developer) can always verify where keyboard focus lives.
- **Active Context section** with `ARROWS/HOME/END · ESC NEXT` hint is a good accessibility aid. It tells the user exactly which keys navigate the current focus context.
- **Footer bar displays full keybinding reference** — all modes have their shortcuts visible.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **A-1** | **Focus Path shows "–" when editor is blurred** | 🟢 Low | When the editor focus is "blurred" (default state), the Focus Path just shows `–`. This is technically correct but unhelpful. Consider showing the last-known path with a dimmed/italic style, so the user can still orient spatially. |
| **A-2** | **Settings panel tab list has no visible keyboard focus ring** | 🟡 Medium | The settings tabs (Atmosphere, Editor, Interaction, etc.) show active state with a filled background, but there's no visible `:focus-visible` ring to distinguish keyboard focus from mouse click. Users navigating with Tab can't tell which item has focus. |
| **A-3** | **Document navigator category tabs may trap focus** | 🟡 Medium | The document nav shows RECENT/CLUSTER/ROLE/REFERENC/ENVIRON tabs with numeric badges. If a user Tabs into this row, it's unclear whether arrow keys navigate between tabs or whether Tab advances out. The `ARROWS/HOME/END · ESC NEXT` hint only shows in the Context Engine, not inline. |

## 4. Selection Mechanisms (Region, Component, Meta/Pragmatic/Syntactic)

### ✅ Strengths
- **Region system is well-exposed at Coarse LoD.** The Regions section clearly shows SIDEBAR (collapsed) and EDITOR (active, with a green dot + highlight). This is the right level of abstraction for spatial orientation.
- **Component-level selection** in the Inspector (AST tab) uses indented tree nodes with position markers (`1:1`, `1:6`, `1:7`). Line:column annotations are concise and useful.
- **Mode shortcuts** at Coarse LoD (i/v/t) and tab shortcuts (AST/TOKENS/FLOW/STEPS) provide rapid region+component switching.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **S-1** | **AST tree nodes have no hover/focus affordance visible** | 🟡 Medium | The AST tree (Seed > Expression > Operation > Frame > Parameter > Literal) shows as plain text with disclosure triangles. There's no visible highlight-on-hover or selected-node state. For a structural selection tool, highlighting the hovered/selected node in the tree — and optionally in the editor — would be a significant UX improvement. |
| **S-2** | **"CURRENT VISUAL · VISUAL" is redundant** | 🟢 Low | In the Active Context section, `CURRENT VISUAL · VISUAL` repeats "VISUAL" twice. This likely means "activation context: Visual" and "perspective: Visual" but the double label is confusing without explanatory differentiation (e.g., `Context: Visual · Perspective: Visual`). |

## 5. Prompting Effectiveness

### ✅ Strengths
- **Lens Walk Starter banner** at the bottom of the viewport is an effective progressive disclosure prompt. It provides clear next-step guidance ("Lens Walk Starter will set level to intermediate") and the "UNLOCK + START" CTA is visually prominent.
- **Step-by-step prompt overlay** (visible in the 375px and 600px screenshots) — "Choose a Seed, STEP 1/7" with descriptive text and NEXT/SKIP buttons — is well-executed. It uses a card overlay pattern that doesn't fully occlude the workspace.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **PR-1** | **Prompt overlay overlaps editor controls at narrow widths** | 🟡 Medium | At 375px and 600px, the "Choose a Seed" prompt card partially overlaps the document selector dropdown ("Simple ▾") and the run button (▶). The user may not be able to interact with these controls without first dismissing or paginating the prompt. |

## 6. Flow & Portability

### ✅ Strengths
- **Breadcrumb navigation** (`Workbench > Editor > AST` or `Workbench > Geology > AST`) updates dynamically. Good wayfinding.
- **Document navigator** supports RECENT/CLUSTER/ROLE/REFERENCE/ENVIRONMENT categories with count badges. The ARCHIVE/DELETE/RENAME actions are accessible inline.
- **COPY/PASTE badge** gives clear mode indication on the Context Engine.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **F-1** | **No visible "back" or "undo navigation" affordance** | 🟢 Low | The breadcrumb shows the current path but doesn't visually indicate clickability for back-navigation. The `>` chevrons suggest hierarchy, but the individual segments don't have hover underline or pointer indication in screenshots. |

---

## 7. Layout & Responsiveness

### ✅ Strengths
- **Three-column → stacked transition** works reasonably. At 1440px: Editor | Inspector | Context Engine side-by-side. At 800px and below, panels stack vertically.
- **Sidebar icon strip** collapses to a narrow icon rail on all viewports. Icons remain accessible.
- **Editor header badge row** wraps gracefully — `VIS · BAS`, `MEDIUM`, `AMBIENT…`, `DOC`, `REF` reflow without clipping.

### ⚠️ Findings

| # | Issue | Severity | Detail |
|---|-------|----------|--------|
| **R-1** | **At 375px, the Geology footer completely overwhelms the viewport** | 🔴 High | The narrow-viewport screenshot shows the Geology footer consuming ~40% of viewport height. Mode badges (NORMAL, GEOLOGY, FINE, BASIC, VISUAL), keybinding hints, context pills, and the Lens Walk prompt all stack vertically into a dense block. The user can barely see the actual content. Consider collapsing footer sections behind a disclosure toggle at narrow widths. |

## Recommended Next Steps

1. **Fix T-1 immediately** — the "Editing" mode button needs a distinct, legible color treatment (e.g., amber/orange fill with dark text, matching the semantic weight of "editing" as a destructive-adjacent action).
2. **Address R-1** — implement a collapsible/minimized footer mode for viewports under 600px. Show only the most critical status (mode + focus) with a toggle to expand the full keybinding reference.
3. **Batch the 🟡 items** into a polish sprint:
   - Add `:focus-visible` outlines to Settings tabs and Document Navigator category tabs.
   - Hover highlights for AST tree nodes.
   - Expand `AMBIENT / MED…` badge or use a shorter label.
   - Add visual grouping separators to the footer bar.
4. **Address 🟢 items** as opportunistic improvements during related work.
